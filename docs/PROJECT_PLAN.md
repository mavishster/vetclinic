## 1. Цель и рамки

**Что строим:** систему управления ветеринарной клиникой — аналог VetManager, который:

- работает **локально** в сети клиники и не зависит от интернета;
- **периодически выгружает данные в облако** — для резервной копии и доступа через интернет.

**Рамки первой версии:** одна клиника (один филиал). Структура данных готова к появлению второго филиала, но интерфейса управления сетью нет.

**Приоритетные модули:** клиенты, медкарты, счета, касса, лаборатория, стационар, товары и услуги, прайс-лист, складской учёт, сотрудники, отчёты.

**Источник требований:** справка VetManager (help.vetmanager.cloud) + практика клиники. VetManager — образец функций, а не образец реализации: что у него сделано неудобно, делаем по-своему (см. раздел 6).

## 2. Как мы работаем

### 2.1. Роли

| Кто | Что делает |
|---|---|
| **Заказчик (клиника)** | Присылает материалы (статьи справки в PDF, скриншоты), объясняет реальные правила работы, проверяет результат на демо, принимает решения по спорным вопросам |
| **Разработчик (Claude)** | Разбирает материалы, проектирует, фиксирует решения, пишет код и тесты, показывает результат |

### 2.2. Цикл работы над модулем

1. **Материалы.** Заказчик присылает статьи справки по модулю (PDF через «Печать → Сохранить как PDF», чтобы сохранились скриншоты).
2. **Разбор.** Что есть в VetManager → что берём → что делаем лучше → что откладываем.
3. **Проект.** Сущности, правила, стыки с другими модулями. Записывается в раздел 6 этого документа; важные решения — отдельным ADR.
4. **Согласование.** Заказчик подтверждает разбор или поправляет.
5. **Реализация** маленькими законченными шагами (одна задача — одна проверяемая часть).
6. **Тесты** на каждое бизнес-правило.
7. **Демо** заказчику → правки → модуль закрыт.

### 2.3. Правило очерёдности

- Модули **операционного уровня** (медкарта, счета, склад, касса, календарь) тесно связаны, поэтому их реализация начинается **только после разбора материалов по всем им**. Статус: разобраны.
- Модули-**«листья»** (стационар, лаборатория, отчёты, зарплата, ЛК) можно разбирать позже — они добавляют новые таблицы и не ломают существующие.
- Слой **ядра и основы** не зависит от неразобранных модулей — с него начинаем код.

## 3. Инженерные принципы

Обязательны для всего кода проекта.

### 3.1. KISS — сначала простое решение

- Используем стандартные средства Django: ORM, миграции, авторизацию, админку для справочников. Своих фреймворков поверх фреймворка не пишем.
- Бизнес-логика — обычные функции в `services.py`. Классы, фабрики и паттерны — только когда функция перестаёт справляться.
- Модульный монолит, а не микросервисы. Журналы движений — обычные таблицы, а не event sourcing.
- Одна задача решается одним способом во всём проекте.

### 3.2. DRY — одно знание в одном месте

Повторяющиеся механики реализуются **один раз** в ядре:

| Механика | Где используется |
|---|---|
| Базовая модель (UUID, даты, автор, версия, мягкое удаление) | Все таблицы |
| Базовый документ (номер, статус, выполнить, откатить) | Счёт, приход, расход, перемещение, инвентаризация, кассовые документы |
| Журнал движений (проводки) | Склад, касса, баланс клиента, долги поставщикам |
| Справочник (добавить, деактивировать, позже — объединить) | Виды, породы, цели обращения, города, улицы, производители, статьи движения денег и др. |
| Подтверждение действия (ПИН / пароль) | Касса, удаление, откаты |
| Печать по шаблону | Медкарта, вакцинации, счёт, договор, этикетки |
| Экран списка с фильтрами | Все списки |

**Правило трёх:** обобщаем при третьем повторении, не раньше. Дублирование дешевле неправильной абстракции.

### 3.3. SOLID — в разумной мере

- **S** — модель хранит данные, сервис содержит правила, view/API только принимают и отдают данные. Модуль меняется по одной причине.
- **O** — новое поведение добавляется подпиской на событие или новой функцией-стратегией, без правки существующего кода (пример: режимы цены «фиксированная» / «наценка»).
- **L** — все документы следуют одному жизненному циклу; код выполнения/отката работает с любым документом.
- **I** — модуль открывает наружу узкий набор функций (`services.py`), а не свои таблицы.
- **D** — модули зависят от публичных функций друг друга, а не от внутренностей. Проверяется `import-linter`.

### 3.4. YAGNI — не делаем того, что пока не нужно

- Функции «на будущее» не реализуем (список отложенного — раздел 9).
- **Исключение — фундамент:** решения, которые почти невозможно добавить позже без переписывания (UUID, поля синхронизации, журналы, базовые единицы, `clinic_id`), закладываем сразу.

### 3.5. Конфликт принципов

**При конфликте побеждает KISS.** Понятный код с небольшим повтором лучше универсального механизма, в котором трудно разобраться.

### 3.6. Практики

- **Тесты** (pytest) на каждое бизнес-правило. Сервисы покрыты тестами всегда; экраны — по необходимости.
- **pre-commit:** `ruff` (стиль и ошибки, форматирование), `import-linter` (границы модулей), `mypy` для `services.py`.
- **ADR** (`docs/adr/NNN-название.md`): что решили, почему, какие были альтернативы.
- **Маленькие коммиты** с понятным описанием (формат Conventional Commits: `feat:`, `fix:`, `refactor:`…).
- **Миграции** проверяются глазами перед применением; данные никогда не удаляются миграцией без отдельного решения.

## 4. Архитектура

### 4.1. Развёртывание

```
┌──────────── Клиника (локальная сеть) ────────────┐          ┌──────── Облако (VPS в РФ) ────────┐
│                                                   │          │                                    │
│  Браузеры сотрудников ──► Локальный сервер        │  HTTPS / │  Копия базы (только чтение)        │
│                           (Docker Compose)        │  WireGuard  Доступ через интернет            │
│                           • Django + API          │ ───────► │  Резервные копии                   │
│                           • PostgreSQL            │ исходящее│  Позже: личный кабинет клиента     │
│                           • Агент синхронизации   │ соединение                                   │
│                           • ККТ (онлайн-касса)    │          │                                    │
└───────────────────────────────────────────────────┘          └────────────────────────────────────┘
```

- Работа клиники не зависит от интернета.
- Соединение с облаком всегда инициирует клиника — белый IP и проброс портов не нужны.
- Синхронизация первой версии — **односторонняя** (клиника → облако).

### 4.2. Модульный монолит: уровни

Верхний уровень может пользоваться нижним, **но не наоборот**.

| Уровень | Модули |
|---|---|
| 4. Надстройки | Стационар · Лаборатория · Отчёты · Зарплата · ЛК клиента · Уведомления |
| 3. Операции | Календарь и приёмы · Медкарта · Счета · Склад · Касса |
| 2. Основа | Клиенты и питомцы · Каталог товаров и услуг · Сотрудники и график |
| 1. Ядро | Базовые модели · Права · Справочники · Аудит · Печать · Синхронизация |

### 4.3. Правила модулей

1. **Таблицы модуля — его личное дело.** Другие модули в них не пишут.
2. **Публичный вход** — `services.py`. Только через него другие модули вызывают модуль.
3. **События** для реакции других модулей («счёт выполнен», «приход выполнен»…).
   - Деньги и остатки обрабатываются **в той же транзакции**: либо всё, либо ничего.
   - Уведомления, SMS, выгрузка в облако — в фоне, после транзакции.
4. **Общие сущности основы** (клиент, питомец, товар, сотрудник) — допустимы прямые ссылки (FK).
5. **Модули можно выключать** (например, без склада счета работают без списания).
6. **Границы проверяются автоматически** (`import-linter`).
7. **Фронтенд** устроен так же: у каждого модуля своя папка с экранами и маршрутами.
8. **API-first:** любое действие доступно через API. Веб-интерфейс — один из клиентов API; мобильное приложение и голосовой ввод станут другими (ADR-019).

## 5. Фундаментальные решения

Каждое оформляется отдельным ADR в репозитории. Пересмотр — только отдельным решением.

| № | Решение | Суть |
|---|---|---|
| ADR-001 | Модульный монолит | Одно приложение, одна БД, модули с публичными интерфейсами |
| ADR-002 | UUID-ключи и поля синхронизации | `id` (UUID), `created_at`, `updated_at`, `created_by`, `updated_by`, `version`, `is_deleted`, `node_id`, `clinic_id` |
| ADR-003 | Мягкое удаление | Физически ничего не удаляется; «удалить» = деактивировать |
| ADR-004 | Журналы движений | Остатки и балансы вычисляются из журналов, куда записи только добавляются; кэш остатков обновляется в той же транзакции |
| ADR-005 | Неизменяемость проведённых документов | Исправление — откатом (если нет зависимых движений) или документом-корректировкой |
| ADR-006 | Остатки в базовых единицах | Склад хранит самую мелкую единицу (таб., мл, шт.); упаковки — пересчёт |
| ADR-007 | Партии ведутся всегда | Нужны для сроков годности, себестоимости, серий вакцин; настройка только прячет их в интерфейсе |
| ADR-008 | Фактическая себестоимость в строке счёта | Пишется закупочная цена списанной партии |
| ADR-009 | Продажа в минус без «временных партий» | Движение «себестоимость ожидается», закрывается следующим приходом |
| ADR-010 | Явные связи вместо совпадений | Медкарта и счёт хранят `appointment_id`; никаких правил «совпал врач» или «в пределах 6 часов» |
| ADR-011 | Деньги и количества | `Decimal`: деньги (12,2), количества (14,3); время — с часовым поясом |
| ADR-012 | Нумерация документов | С префиксом узла (`К1-000123`) — без конфликтов при синхронизации |
| ADR-013 | Права | Роль × модуль × действие (просмотр, редактирование, удаление, администрирование) + точечные права |
| ADR-014 | Подтверждение операций ПИН-кодом | Короткий ПИН сотрудника для кассы, откатов, удаления; пароль — для входа и админ-операций |
| ADR-015 | Цена фиксируется в строке счёта | В момент добавления строки; не меняется до оплаты |
| ADR-016 | Наценка: «пусто = наследовать» | Пустое значение берёт наценку группы; 0 — это действительно 0 |
| ADR-017 | Цены в комбинациях | `price_override` пусто → текущая цена прайса; задано → фиксированная |
| ADR-018 | График — одна модель | Всегда интервалы работы; смена — необязательная группировка со старшим |
| ADR-019 | API-first | Все функции доступны через API; бизнес-логика не зависит от того, какой клиент её вызывает |
| ADR-020 | Адаптивные экраны врача | Медкарта, календарь, стационар, карточка пациента с самого начала работают на телефоне и планшете |
| ADR-021 | Всё в Linux-контейнерах | Разработка на macOS, сервер на Windows; код не зависит от ОС. На сервере — Ubuntu в Hyper-V (рекомендуется) или Docker Desktop + WSL2. Драйвер ККТ — на Windows-хосте, контейнер обращается к нему по сети |
| ADR-022 | Учётная запись в ядре | `core.User` (логин, ФИО, права); профиль сотрудника (должность, график, склад) — в модуле staff. Кто действует — `core.context` |

## 6. Модули: статус и проект

Статусы: ✅ разобран · 🟡 частично · ⬜ не разобран.

### 6.1. Ядро ✅

- Базовая модель, базовый документ, журнал движений, справочник (см. 3.2).
- Справочник: название (уникально без учёта регистра среди неудалённых), «активна». Деактивация — запись не предлагается для выбора, но остаётся в старых документах; удаление — мягкое, для ошибочных записей. Уникальность может считаться в пределах поля (порода — в пределах вида). Общий API: фильтры `active`, `search` и поля модели.
- Пользователи, роли, права (ADR-013), ПИН-коды (ADR-014). Роль — группа Django; права назначаются на модуль целиком (просмотр / редактирование / удаление); API проверяют права роли.
- ПИН: 4–6 цифр, не тривиальный; задаёт сотрудник сам, подтверждая паролем; 5 неверных попыток — блокировка на 15 минут; администратор может сбросить.
- Журнал аудита (кто, что, когда изменил) — django-simple-history для всех моделей на `BaseModel` и для пользователей (без пароля и ПИН). В админке — кнопка «История».
- Нумерация документов (ADR-012): `K1-000123`, свой счётчик для каждого типа документа на узле, без пропусков и повторов при одновременной работе.
- Базовый документ: черновик → выполнен → (откат) → черновик. Выполнение и откат — в одной транзакции вместе с проводками и реакциями других модулей; выполненный документ не изменяется и не удаляется; повторное выполнение исключено блокировкой.
- Журнал движений: записи только добавляются; откат — обратными записями с датой отката (отчёты «на дату» не меняются задним числом).
- События `document_executed` / `document_rolled_back` — получатели в той же транзакции.
- Фоновые задачи: Django-Q2, очередь в PostgreSQL, отдельный сервис `worker`. `run_in_background()` ставит задачу только после фиксации транзакции и сохраняет пользователя для аудита.
- Печать по шаблону: Jinja2-шаблоны с переменными (`{{ clinic.name }}`, позже `{{ client.fio }}`, `{{ visit.diagnosis }}`…) в песочнице, PDF через WeasyPrint (шрифт DejaVu с кириллицей). Модули регистрируют свои виды форм с переменными и примером данных; общие переменные — клиника, сотрудник, дата. Фильтры: `money`, `qty`, `date`, `datetime`. Ошибка в шаблоне — понятное сообщение с номером строки. Визуальный редактор шаблонов — вместе с экранами модулей (этап 3).
- Настройки клиники (ключ-значение с типами).

### 6.2. Клиенты и питомцы ✅

**Клиент:** ФИО (фамилия обязательна), паспорт, город (обяз.), улица, дом/квартира, индекс, email, скидка %, номер по журналу, тип, источник («как нашли»), отказ от рассылок, чёрный список, описание, дисконтная карта, статус (активный / неактивный / временный).

- Телефоны — отдельная таблица (тип, номер в нормализованном виде, основной).
- Договоры — записями (номер, дата, срок, файл); «договор заключён» вычисляется.
- Файлы с категориями (Общий, Договор…); удалять договоры — отдельное право.
- Баланс — из журнала `client_ledger`, не хранится в карточке.

**Правила:**
- Поиск дублей по ФИО (`pg_trgm`) и телефону (последние 10 цифр) — до сохранения.
- Обязательные поля настраиваются клиникой.
- «Удалить» = деактивировать, с подтверждением; восстановление — «Активировать».
- Временный клиент (быстрая запись): имя, телефон, кличка + проверка дублей по телефону.

**Питомец:** кличка, вид, порода (все обязательны), пол (самец/самка/неизвестно), стерилизован, окрас, дата рождения (+ признак «приблизительная»), чип, лаб. №, примечание, статус (активный / передан / умер / удалён), дата смерти. Вес — история `pet_weight`.

- Возраст не хранится — вычисляется.
- Смена владельца: таблица `pet_ownership` (питомец, клиент, с, по). Медкарта уходит с питомцем, счета остаются у прежнего владельца.

### 6.3. Каталог товаров и услуг ✅

**Позиция (`item`):** тип (товар / услуга / комбинация), название, описание, группа, артикул, для продажи, только для комбинаций, базовая единица учёта, штрихкод хранения, себестоимость вручную (услуги, товары без учёта), налоговый профиль, «вызов».

**Единицы (`item_unit`):** единица, сколько базовых единиц в ней, для продажи / для закупки, цена фиксированная **или** наценка % (пусто = от группы), min/max цены, правило округления, штрихкод.

**Группа:** тип, наценка %, налоговый профиль, «показывать в вакцинах», категория для зарплаты.

**Услуга:** ответственные сотрудники (`service_responsible`) — при добавлении в счёт первыми предлагаются те, кто в смене.

**Комбинации:** шаблонная (просто вставка набора позиций) или обычная (одна строка со составом, свои цены по ADR-017, режим печати: все позиции / только имя / детализация по услугам / имя и состав без цен).

**Цена:** фиксированная → как задано; наценка → своя или группы × закупочная цена (FIFO или последняя партия — настройка) → округление. История цен.

### 6.4. Сотрудники, график, календарь ✅ (зарплата — ⬜)

**Сотрудник:** ФИО, должность, роль, склад по умолчанию, ПИН, активен.

**График:** `work_interval` (сотрудник, начало, конец — через полночь допустимо, тип, смена), `interval_type` (рабочий / нет, цвет), `interval_template`, `shift` (старший смены) + `shift_member` (ставка на момент смены), `holiday`. Копирование дня и недели.

**Приём (`appointment`):** клиника, клиент, питомец, врач, цель обращения, начало, конец, статус, заметка, источник, время прихода / начала / завершения, причина отмены, `parent_id`.

- Статусы: запланирован → пришёл (ожидает) → у врача → завершён; отдельно — отменён (с причиной), не пришёл.
- «Просрочен» — подсветка, не статус.
- Открытие медкарты по записи переводит приём в «у врача».
- Предупреждения: врач занят, врач не в графике, клиент уже записан сегодня.
- Фильтры календаря показывают, сколько записей скрыто.

**Цель обращения:** название, длительность по умолчанию, цвет, показывать в ЛК, служебный признак (вакцинация / анализ / …).

### 6.5. Медкарта ✅

**Запись (`visit`):** питомец, клиент (владелец на момент приёма), врач (обяз.), дата-время, цель (обяз.), результат, приём, вес, температура, описание лечения, рекомендации и назначения, рекомендации по питанию, дата следующего визита.

- Диагнозы — `visit_diagnosis` (с типом: предварительный / окончательный).
- Позиции прайса в тексте через `@` → `visit_item` (раздел: лечение / рекомендации) → «Добавить в счёт».
- Текстовые шаблоны (личные и общие).
- Спецшаблоны — структурированные данные: `study_template` (схема полей, нормы по видам) + `visit_study` (значения JSONB). Не хранятся внутри HTML.
- Автосохранение черновика.
- Обязательность веса / результата / диагноза — настройки.

**Вакцинация:** приём, питомец, вакцина (позиция каталога), **партия со склада** (серия и срок подставляются), количество, дата, тип (первичная / вторичная), следующая дата (кнопки 3 нед. / мес. / год), статус напоминания. Новая вакцинация закрывает напоминания по той же вакцине / группе. «Запланировать визит на дату повтора» создаёт приём.

### 6.6. Счета 🟡 (не разобраны: окно оплаты, правка выполненного счёта, правила скидок)

**Счёт:** номер, клиент, питомец, врач, приём, клиника, вызов, ночной приём, скидка и надбавка (% или сумма), суммы (по позициям / общая / к оплате = общая − баланс), статус, примечание, быстрый счёт.

**Строка:** позиция, единица, количество (+ в базовых единицах), цена (в пределах min/max), признак ручной цены (скидка не применяется), скидка, сумма, исполнитель, склад, партия, фактическая себестоимость, `parent_line_id` (состав комбинации).

- Статусы: черновик (отложен) → выполнен → оплачен частично → закрыт; удалён.
- Окно: прайс с поиском (по слову, артикулу, штрихкоду), фильтр складов (запоминается), горячие клавиши (Enter, +/−, `/`, Ctrl+Enter, Shift+Enter), режим сканера, последняя медкарта.
- Вакцина в счёте → предложение записать вакцинацию (настройка).
- **Быстрый счёт:** клиент «Гость» (настройка клиники), оплата в том же окне, подсказка сдачи, баланс клиента не затрагивается.
- Ночной приём → надбавка из настроек (по умолчанию 100%).

### 6.7. Склад ✅

**Склад:** название, тип (хранение / реализация — списание по счетам только с реализации), ответственный.

- Ответственный проводит документы своего склада; право «проводить по любым складам» — для руководителя.
- Смена ответственного — документ передачи склада с подтверждением обеими сторонами.

**Партия:** товар, строка прихода, серия, срок годности, дата изготовления, производитель, закупочная цена за базовую единицу, НДС, штрихкод партии, (позже) код маркировки.

**Документы:** приход, расход (с причиной списания), перемещение, инвентаризация, возврат поставщику.

- Черновик → выполнен → откачен. Откат — только если нет зависимых движений.
- Правка закупочной цены в выполненном приходе — как исправление: с даты накладной, пересчёт себестоимости проданного, запись в аудит.
- Инвентаризация: мастер (все / как в прошлый раз / вручную или по группам / сканером), учётное и фактическое по партиям, ввод в любых единицах, выгрузка и загрузка Excel, отчёт излишков и недостач.
- Продажа в минус — по настройке, ADR-009.
- Контроль: минимальный остаток и истекающий срок (`stock_alert_rule`) → список → создать приход / расход.
- «Экономика» прихода: закупка, цена продажи, наценка было → стало; подсветка, где цена продажи не пересмотрена.
- Печать этикеток со штрихкодами.
- Взаиморасчёты с поставщиками — журнал `counterparty_ledger`.

**Отчёты склада:** оборотка по товару и по всем, остаток на дату, остатки на 1-е числа месяцев, взаиморасчёты с поставщиками, результаты инвентаризации; выгрузка в Excel.

### 6.8. Касса 🟡 (не разобран: фискальный регистратор)

**Касса:** название, тип (операционная / сейф / банк), главная, ответственный, ККТ.

**Документы:** оплата счёта, приход (ПКО), расход (РКО), закрытие кассы, передача ответственного, перевод в другую кассу, возврат клиенту, передача в банк.

- Обязательные поля ордера: касса, дата выполнения, статья, контрагент, сумма, назначение.
- Проводит ответственный (или право «по любой кассе»), подтверждение ПИН-кодом.
- Передача денег / кассы — двухшаговая: ожидает приёма → принят / отменён; получатель видит уведомление.
- Закрытие: безнал уходит в кассу «банк»; **пересчёт наличных** с фиксацией расхождения; закрытие операционной кассы с ККТ закрывает фискальную смену.
- Оплата нескольких счетов одной суммой — `payment_allocation`.
- Остаток кассы всегда вычисляется из журнала.
- Справочники: статьи движения денег (`cash_flow_article`), контрагенты (`counterparty`, общий со складом).
- Возврат клиенту — по умолчанию через фискальный чек возврата (уточнить с бухгалтером, 54-ФЗ).

**Отчёты:** журнал выручки, X-отчёт, оборотная ведомость, остатки, прибыль по группам, движение денег по статьям.

### 6.9. Стационар ⬜ · Лаборатория 🟡 · Отчёты ⬜ · Зарплата ⬜

Ожидают материалов (раздел 10). Известно:
- **Лаборатория** опирается на спецшаблоны медкарты (`study_template` / `visit_study`).
- **Зарплата** читает исполнителей и суммы из строк счетов и интервалы / смены из графика (ставка за смену, оплата по часам, процент от услуг, процент от счетов старшего, категории для зарплат).
- **Отчёты** только читают данные; список — по реальной практике клиники, а не «все отчёты VetManager».

### 6.10. Синхронизация и облако 🟡

- **Шаг А (первая версия):** клиника → облако. Логическая репликация PostgreSQL через WireGuard; облако только для чтения. Ночной `pg_dump` с шифрованием в S3-хранилище + файлы вложений.
- **Шаг Б (позже, по необходимости):** двусторонняя — `outbox`, идемпотентность по UUID, «последняя запись побеждает» для карточек, финансовые документы создаются только на одном узле.

### 6.11. Личный кабинет клиента ⬜ (отложен, материалы разобраны)

Облачная часть на данных шага А: главная, визиты, вакцинации, анализы, рекомендации, документы, профиль. Вход по ссылке с токеном (хранится хеш, срок, отзыв). Видимость визитов по целям обращения. Медкарта видна через 60 минут после создания. Смена email и онлайн-запись — через очередь входящих заявок.

### 6.12. Голосовой ввод ⬜ (этап 8, требования собраны предварительно)

**Цель:** врач заполняет медкарту голосом, не отвлекаясь от пациента.

**Два уровня:**
1. **Диктовка** — речь превращается в текст в текущем поле (описание лечения, рекомендации). Просто и надёжно.
2. **Умное заполнение** — врач надиктовывает приём целиком, система раскладывает текст по полям: жалобы, осмотр, вес, температура, диагноз, рекомендации, позиции прайса (`@`). Врач проверяет черновик и подтверждает.

**Правила:**
- Голос создаёт только **черновик** — сохраняет и отвечает за запись врач.
- Аудио по умолчанию **не хранится**, хранится только текст.
- Словарь подсказок для распознавания: названия препаратов из каталога, диагнозы, породы — сильно повышает точность на ветеринарной лексике.

**Провайдер распознавания — за единым интерфейсом** (`transcribe(audio) → text`, `structure(text) → черновик`), чтобы его можно было сменить без переделки медкарты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| faster-whisper на локальном сервере | Данные не покидают клинику, работает без интернета, бесплатно | Нужен мощный сервер (лучше с видеокартой) |
| Yandex SpeechKit / SaluteSpeech | Высокое качество, серверы в РФ, слабое железо не нужно | Платно (поминутно), нужен интернет |
| Web Speech API браузера | Ничего не нужно ставить | Аудио уходит в Google, ненадёжно в РФ — **не используем** |

Умное заполнение требует языковой модели (YandexGPT / GigaChat в облаке или локальная модель) — решается на этапе 8.

**Что закладываем сейчас:** только чистый сервис создания черновика медкарты из структурированных данных (он нужен и без голоса). Остальное — YAGNI до этапа 8.

### 6.13. Мобильное приложение ⬜ (этап 8, требования собраны предварительно)

**Кто и зачем:**
- **Врач:** медкарта и пациенты на обходе стационара, отметки о выполнении назначений, фото с камеры прямо в медкарту, голосовой ввод.
- **Руководитель:** выручка, касса, загрузка врачей, остатки — удалённо.
- **Клиенты** — личный кабинет (6.11), это веб, отдельное приложение не нужно.

**Подход (KISS + DRY):** тот же код фронтенда Vue/Quasar.
1. Сначала **PWA** — веб-приложение, которое ставится на телефон иконкой. Отдельной разработки почти не требует.
2. При необходимости камеры, push-уведомлений, публикации в магазинах — сборка через **Capacitor** из того же кода.

**Где работает:**
- **В клинике (Wi-Fi):** напрямую с локальным сервером — полный доступ.
- **Вне клиники:** просмотр через облако (шаг А синхронизации — только чтение). Изменения вне клиники — через VPN (WireGuard) к локальному серверу или после двусторонней синхронизации (шаг Б).
- **Офлайн-режим** — отложен (YAGNI).

**Что закладываем сейчас:** API-first (ADR-019) и адаптивные экраны врача (ADR-020). Это дёшево сейчас и дорого потом.

- 8.2 Голосовой ввод: диктовка в поля медкарты, словарь подсказок.
- 8.3 Умное заполнение медкарты из диктовки.
- 8.4 При необходимости — Capacitor-сборка, push-уведомления, доступ вне клиники через VPN.
- **Готово, когда:** врач ведёт приём и обход с телефона, медкарта заполняется голосом с проверкой врача.

### Этап 9. Отложенное
- См. раздел 9 — по мере необходимости.

## 9. Отложено (YAGNI)

Не делаем, пока не появится реальная потребность:

- Вскрытые флаконы со сроком годности после вскрытия.
- Инвентаризация без остановки продаж (учёт продаж во время подсчёта).
- Доступ по IP.
- Двусторонняя синхронизация (шаг Б).
- Интерфейс управления сетью филиалов, цены по филиалам.
- Объединение дублей в справочниках (сначала только деактивация).
- «Честный знак»: приёмка, продажа, частичное выбытие.
- Импорт приходных накладных из файлов поставщиков / ЭДО.
- Интеграция с лабораторным оборудованием (Idexx и др.).
- Кабинеты и оборудование как ресурсы календаря.
- Офлайн-режим мобильного приложения.
- Хранение аудиозаписей приёмов.

## 11. Открытые вопросы

Решаются по ходу; ответ фиксируется здесь и при необходимости в ADR.

- Сервер: Windows Server или Windows 10/11 Pro, выделенный ли компьютер, характеристики (ЦП, ОЗУ, диск, видеокарта — важно для голосового ввода) → способ запуска контейнеров (ADR-021).
- Модель ККТ в клинике (АТОЛ / Штрих-М / другая) и способ подключения.
- Система налогообложения, ставки НДС → налоговые профили позиций.
- Возврат денег клиенту без фискального чека — допустим ли (вопрос бухгалтеру).
- Принтер этикеток и сканер штрихкодов — какие есть.
- Облачный провайдер и тариф.
- Голосовой ввод: локальное распознавание или облачное (зависит от сервера, бюджета и стабильности интернета) — к этапу 8.
- Какие телефоны / планшеты у врачей, есть ли Wi-Fi во всех кабинетах и стационаре — к этапу 8.

## 13. Критерии готовности задачи (Definition of Done)

Задача считается сделанной, когда:

- [ ] бизнес-правила реализованы в `services.py`, а не в view или модели;
- [ ] на каждое правило есть тест, все тесты проходят;
- [ ] ruff, mypy, import-linter без ошибок;
- [ ] миграции проверены;
- [ ] новые решения зафиксированы (этот документ или ADR);
- [ ] показано заказчику (для пользовательских функций).
