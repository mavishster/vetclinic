# Правила разработки

Обязательны для всего кода проекта. Подробности и причины — `docs/PROJECT_PLAN.md`, раздел 3, и `docs/adr/`.

## Принципы

- **KISS.** Сначала простое решение. Стандартные средства Django (ORM, миграции, авторизация, админка) вместо своих механизмов. Логика — обычные функции в `services.py`; классы и паттерны — только когда функции перестают справляться.
- **DRY.** Одно знание — в одном месте. Общие механики (базовая модель, документ, журнал движений, справочник, подтверждение ПИН, печать, экран списка) — один раз в ядре. **Правило трёх:** обобщаем при третьем повторении, не раньше.
- **SOLID — в разумной мере.** Модель хранит данные, сервис содержит правила, API только принимает и отдаёт данные. Новое поведение — через события и новые функции, а не правкой старого кода. Модули открывают наружу узкий набор функций.
- **YAGNI.** Не делаем «на будущее» (список отложенного — PROJECT_PLAN, раздел 9). Исключение — фундамент, который потом не добавить без переписывания (ADR-002…012).
- **При конфликте принципов побеждает KISS.**

## Правила модулей

1. Таблицы модуля — его личное дело. Другие модули в них не пишут.
2. Другие модули вызывают модуль только через его `services.py`.
3. Реакция на чужие действия — через события. Деньги и остатки — в той же транзакции; уведомления и выгрузка — в фоне.
4. На общие сущности основы (клиент, питомец, товар, сотрудник) можно ссылаться напрямую (FK).
5. Верхний уровень может пользоваться нижним, но не наоборот: ядро ← основа ← операции ← надстройки.
6. Любое действие доступно через API (ADR-019).

Правила 2 и 5 проверяются автоматически (`lint-imports`, контракты в `backend/pyproject.toml`).

## Структура модуля

```
<модуль>/
├── models.py      # данные
├── services.py    # публичный вход и бизнес-правила (типизирован, проверяется mypy)
├── api/           # приём и отдача данных, без бизнес-логики
├── admin.py       # при необходимости
├── migrations/
└── tests/         # тест на каждое бизнес-правило
```

## Код

- Деньги — `Decimal(12,2)`, количества — `Decimal(14,3)`; `float` для денег и количеств запрещён (ADR-011).
- Время — всегда с часовым поясом.
- Все модели наследуют `core.models.BaseModel`: UUID, служебные поля, мягкое удаление (ADR-002, ADR-003). Деньги и количества — `core.fields.MoneyField` и `QuantityField`.
- Новый справочник: модель наследует `core.models.Directory`, API — `core.api.directories.DirectoryViewSet`, админка — `core.admin.DirectoryAdmin`. Обычно это несколько строк (пример — `clients`: виды и породы).
- Ничего не удаляется физически (ADR-003). Проведённые документы не редактируются (ADR-005).
- Кто действует: в веб-запросах заполняется автоматически; в фоновых задачах и командах оборачивайте код в `with acting_user(user):` (ADR-022).
- Имена в коде — на английском, тексты для пользователя и комментарии — на русском.
- Зависимости закрепляются точной версией. Обновление — отдельный осознанный коммит.

## Проверки

Перед коммитом — `pre-commit` (стиль, форматирование). Перед отправкой — `make check`:

- `ruff` — стиль и типичные ошибки;
- `mypy` — типы в `services.py`;
- `lint-imports` — границы модулей;
- `pytest` — тесты;
- проверка, что миграции созданы.

CI запускает те же проверки на каждый push.

## Решения

Важное решение оформляется ADR в `docs/adr/` (шаблон — `000-template.md`) и отражается в `docs/PROJECT_PLAN.md`. Сначала решение, потом код.

## Коммиты

Маленькие, с понятным описанием в формате Conventional Commits: `feat: ...`, `fix: ...`, `refactor: ...`, `docs: ...`, `test: ...`, `chore: ...`.

## Задача готова, когда

- [ ] правила реализованы в `services.py`;
- [ ] на каждое правило есть тест, все тесты проходят;
- [ ] `make check` без ошибок;
- [ ] миграции проверены;
- [ ] решения зафиксированы (PROJECT_PLAN или ADR);
- [ ] показано заказчику (для пользовательских функций).
